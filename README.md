# tk_cdc
Сервис инвалидации кеша Redis для PostgreSQL. Сервис подключается к БД как логический репликационный клиент, читает поток изменений из WAL и удаляет соответствующие ключи в Redis при *UPDATE* или *DELETE* операциях.

> [!TIP] 
> Когда данные в базе изменяются, в кеше соответствующие данные становятся неактуальными. Вместо удаления кеша из приложения сервис читает данные из WAL и производит инвалидацию централизованно.

# Как это работает
Сервис подключается к PostgreSQL как **репликационный клиент**, создает или использует имеющийся **репликационный слот** и подписывается на публикацию. Необходимо установить логический уровень WAL (`wal_level=logical`).

> [!note] 
> Для работы необходимо создать 2-х пользователей в PostgreSQL, один для чтения WAL, второй для осуществления операций чтения LSN и проверки слота репликации.

Сервис читает WAL и отслеживает изменения в определенных таблицах. При изменении в отслеживаемых таблицах сервис производит маппинг измененных записей в Redis-ключи и удаляет. По шагам:
1) В базе данных происходит операция `UPDATE` или `DELETE` в отслеживаемой таблице
2) Сервис читает WAL и видит какие записи были удалены/изменены
3) На основе этих данных сервис формирует ключи Redis и удаляет их с помощью `UNLINK`

> [!warning] 
> Сервис производит **только удаление** неактуальных ключей из Redis. То есть при `UPDATE` отслеживаемой записи соответствующий ключ в Redis тоже удалится.


Поддерживаются флаги:
- `-config` - путь к файлу конфигурации, по умолчанию `./tk_cdc_config.yml`
- `-port` - порт, через который будет происходить обращение к `/healthz` и `/ready` эндпоинтам, по умолчанию `8080`

Все настройки производятся через `.yml` файл конфигурации. При отключении производит автоматическое переподключение к Redis и PostgreSQL. За сохранения LSN последней обработанной записи сервиса отвечает PostgreSQL.
Сервис использует библиотеки `pgx` и `pglogrepl` для операций с PostgreSQL и `go-redis/v9` для взаимодействия с Redis. Подробнее с зависимостями можно ознакомиться в `go.mod`

# Как начать
1) Скачать проект `git clone https://github.com/Tkach360/tk_cdc`
2) Собрать *Docker-образ* `sudo docker build -t tk_cdc .`
3) Настройте ваш PostgreSQL:
	1) Создать 2-х пользователей, одного для чтения WAL, второго для проверки наличия слота репликации и получения LSN:
	```SQL
	-- пользователь для чтения WAL
	CREATE USER tkcdc_replication_user WITH LOGIN PASSWORD 'tkcdc_replication_pass' REPLICATION;
	GRANT CONNECT ON DATABASE your_db TO tkcdc_replication_user;
	
	-- пользователь для операций
	CREATE USER tkcdc_user WITH LOGIN PASSWORD 'tkcdc_pass' REPLICATION;
	GRANT CONNECT ON DATABASE your_db TO tkcdc_user;
	GRANT SELECT ON pg_replication_slots TO tkcdc_user;
	```
	
	2) Создать публикацию с отслеживаемыми таблицами:
	```SQL
	-- можно указать определенные таблицы
	CREATE PUBLICATION tkcdc_publication FOR ALL TABLES;
	```

	3) Опционально создать слот репликации, в противном случае сервис сам создаст его при запуске
	```SQL
	SELECT pg_create_logical_replication_slot('tkcdc_slot', 'pgoutput');
	```
	4) Postgres должен быть запущен раньше сервиса

4) Поднять Redis
5) Настроить `config.yml` сервиса:
```yml
postgres:
  addr: localhost:5432
  db: your_db
  reconnect_max_attempts: 3
  reconnect_delay_ms: 5000

  # пользователь для чтения репликации
  replication_user: tkcdc_replication_user
  replication_pass: tkcdc_replication_pass

  # отдельный пользователь для выполнения операций проверки наличия слота и получения LSN
  app_user: tkcdc_user
  app_pass: tkcdc_pass

  # имя слота логической репликации
  # если слот не существует - сервис попытается создать его при старте
  replication_slot: tkcdc_slot

  # плагин декодирования сообщений WAL, важно для формата сообщений
  plugin: pgoutput

  # имена публикаций, которые отслеживаем через запятую
  publication_names: tkcdc_publication

redis:
  addr: localhost:6379

  # возможна настройка пользователей
  #user: tkcdc_user
  #password: tkcdc_pass

  # номер логической базы данных в Redis
  db: 0

  # кол-во повторных попыток выполнения запросов redis
  query_max_attempts: 3
  query_delay_ms: 10

mapping:
  # схема таблицы по-умолчанию, будет подставляться к каждой таблице, у которой не указана схема
  default_schema: public
  rules:
    - table: users # имя таблицы postgres, чьи поля нужно отслеживать
      # таблица должна иметь PK или иметь UNIQUE NOT NULL поле с настроенным REPLICA IDENTITY USING INDEX
      # для однозначной идентификации записи

      # шаблон ключа в redis, который будет удаляться при изменении строки в postgres
      # в фигурных скобках указано имя поля в postgres (обычно PK), значение которого будет подставляться
      # поддерживаются составлные ключи "user:{id}:{name}"
      # ! ключи в redis плоские, удаление "user:123" НЕ удалит "user:123:email"
      key_pattern: user:{id}
```
5) Запустить сервис через (docker, docker-compose или на хосте) передав ему флаги `-config` и `-port`

# Тестирование
В проекте имеются unit-тесты, интеграционные тесты, а также возможность поднять тестовое окружение для ручного тестирования.

### Запуск всех тестов
```bash
go test ./...
```
### Unit-тесты
```bash
go test ./<модуль>
```
Для unit-тестов использовалась стандартная библиотека `testing` и библиотека `testify`
### Интеграционные тесты
```bash
go test ./tests
```
Для интеграционного тестирования использовалась библиотека `testcontainers-go`

### Запуск демонстрационного окружения
```bash
docker compose up
```
Запускает экземпляры docker контейнеров PostgreSQL, Redis и tk_cdc. Конфигурация tk_cdc берется из `/configs/demo_config.yml`. База данных настраивается через `/demo/postgres_init/01_demo_settings.sql`, которая настраивает PostgreSQL для работы с tk_cdc и создает таблицу `users(id INT, name TEXT, email TEXT)` заполненную данными в базе данных `demo`.

Настройки контейнеров в `docker-compose.yml`
